## Open Code Review

### 是什么

AI 驱动的代码审查 CLI 工具。前身是阿里集团内部官方 AI 代码审查助手，服务数万内部开发者两年，识别数百万代码缺陷。

### 为什么不用通用 Agent 做代码审查

三个问题：
1. **覆盖不全**——Agent 在大变更上"偷懒"，只选择性审查部分文件
2. **位置偏移**——报告的问题与实际代码位置不匹配
3. **不稳定**——自然语言驱动的 Skill 难以调试，审查质量随 prompt 微小变化而波动

根因：纯语言驱动架构缺乏对审查过程的强约束。

### 核心架构：确定性工程 × Agent 混合

**确定性工程处理：**
- 精确文件过滤（审查哪些文件、跳过哪些）
- 智能文件捆绑（相关文件如 message_en.properties 和 message_zh.properties 作为一个审查单元）
- 精细规则匹配（模板引擎，比纯语言驱动更稳定）
- 外部注释定位和反思模块

**Agent 处理：**
- 场景特定 prompt 调优
- 从生产 trace 数据蒸馏的精选领域特定工具集

## 减少漏报（False Negatives）

漏报根因分类："看不到"（缺少上下文）、"看太多"（噪声稀释注意力）、"想不动"（静态 CoT/工作流无法处理多步推理）

**对策：**

1. **文件捆绑**——相关文件在一个上下文中一起审查
2. **Plan Phase**——大变更（≥n 行）先创建结构化审查计划
3. **Agent 动态上下文召回**——每个审查子任务是独立 Agent 循环（最多 20 轮工具调用），模型动态调用 file_read、code_search（git grep）、file_read_diff、file_find
4. **精选工具集**——从生产 trace 数据蒸馏（调用频率分布、重复调用率、新工具对调用链的影响分析）

---

## 减少误报（False Positives）

1. **Reflection Model**——专门训练的 Qwen3-30B-A3B 模型，从用户反馈数据（adopted/false-positive/ignored）中训练。用专家标注做锚点，训练多个不同噪声比例的模型协同标注。假阳性拦截率从 30.09% 提升到 52.63%；推理时间从 5 秒降到 500ms 以下
2. **精细规则模板**——glob 模式匹配规则到特定文件类型（Java 规则给 Java，SQL 规则给 MyBatis XML）
3. **上下文隔离**——分治策略防止跨审查任务的交叉污染

---

## 注释定位准确率（内部 97%+）

三层渐进定位策略：

1. **Layer 1: Hunk-based 文本匹配**——模型提供 `existing_code`（被注释的代码片段）而非行号；系统解析 diff hunks 并通过归一化连续行匹配
2. **Layer 2: 全文件内容扫描**——hunk 匹配失败时回退
3. **Layer 3: LLM 重定位模型**——两层都失败时（模型损坏了代码片段），专门的 Qwen3-8B 模型从 diff 中重新提取精确代码；内部成功率从 37.35% 提升到 85.65%

---

## 四层规则穿透机制

规则使用 first-match-wins 策略：

| 优先级 | 来源 | 示例 |
|--------|------|------|
| 1（最高） | CLI 参数 `--rule <path>` | 一次性覆盖 |
| 2 | 项目级 `.opencodereview/rule.json` | 团队规则，版本控制 |
| 3 | 用户级 `~/.opencodereview/rule.json` | 个人偏好 |
| 4 | 系统默认 | 13 个内置语言/文件类型规则集 |

**内置规则覆盖：** Java（NPE、线程安全、N+1 查询）、TypeScript/React（Hooks 规则、XSS、严格 ===）、C（malloc/free 配对、缓冲区溢出）、MyBatis XML（${} vs #{} SQL 注入）、Maven/Gradle（SNAPSHOT 泄露）

## AACR-Bench

### 规模

- 200 个真实 PR
- 50 个热门开源仓库
- 10 种编程语言
- 80+ 高级工程师标注

### 评测结果

| 指标 | Open Code Review | Claude Code | Codex |
|------|-----------------|-------------|-------|
| 精度 | 25-38% | 7-16% | ~27.8% |
| 最佳召回 | ~20%（Claude-4.6-Opus） | **28.90%**（Claude-4.6-Opus） | 4.92% |
| 最佳 F1 | **25.10%** | 14.13% | 低 |
| Token 消耗 | 352K-743K | 2,062K-5,664K | ~525K |
| 时间 | 1-6 分钟 | 5-14 分钟 | ~3 分钟 |

### 关键发现

1. **更新的模型不一定更好**——Claude-4.8-Opus 精度最高（37.80%）但召回率显著低于 Claude-4.6-Opus，更强的模型可能采用更严格的标准，牺牲覆盖率换精度
2. **Open Code Review 在 F1 上领先**，且 token 效率远高于 Claude Code
3. **Claude Code 召回率最高**（适合安全审计等"宁可多报不可漏报"场景）

## 工具集蒸馏

不是用通用 Agent 工具集，而是分析真实工具调用轨迹：
- 调用频率分布
- 重复调用率
- 新增工具对调用链的影响分析

从中精选领域特定工具集。这是从生产数据中的行为克隆/策略蒸馏。

---

## Reflection Model 训练

从噪声用户反馈中训练假阳性过滤模型：
- 标签：adopted（采纳）、false-positive（误报）、ignored（忽略）
- 噪声问题："ignored" 类别混合了正确和不正确的数据
- 解决方案：用专家标注和明确用户反馈做锚点，训练多个不同噪声比例的模型协同标注，从噪声数据中识别可靠样本
- 参考论文：https://arxiv.org/pdf/2602.20166v1

## 实践验证

Open Code Review 开源版本本身完全由 Claude Code 用 Go 构建（重写内部 Java 系统）。然后用 Open Code Review 审查开发过程中的每次变更。**106 次代码变更中发现 145 个有效问题**，包括：严重 bug/逻辑错误、安全问题、不当错误处理、命名/拼写错误、DRY 违规、性能问题、shell 脚本问题、React/前端问题、国际化不完整。

> "AI 写代码和 AI 审查代码是根本不同的能力。"

## 关键洞察

1. **确定性工程约束 > 纯语言驱动**：代码审查需要硬约束，不能靠 prompt "说服"
2. **小模型可以大幅超越大模型**：Qwen3-8B 定位模型成功率从 37.35% 到 85.65%
3. **从噪声反馈中训练**：Reflection Model 的训练方法适用于所有从用户反馈学习的场景
4. **工具集蒸馏**：从生产 trace 中精选工具比通用工具集更有效
5. **AACR-Bench 是现成的评测基准**：可直接用于代码 Agent 评测
