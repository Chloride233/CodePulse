## 核心概念

### Anthropic 术语体系

| 术语 | 定义 |
|------|------|
| Task | 独立测试用例，有明确输入和成功标准 |
| Trial | 一次任务尝试（同一任务跑多次，因为输出有随机性） |
| Grader | 评分逻辑，一个任务可以有多个 Grader |
| Transcript | 完整的试运行记录（所有工具调用、推理步骤、中间结果） |
| Outcome | 试验结束时的环境最终状态（不是 Agent 说了什么，而是环境实际状态） |
| Evaluation Harness | 端到端运行评测的基础设施 |
| Agent Harness (Scaffold) | 让模型作为 Agent 运行的系统 |
| Evaluation Suite | 测量特定能力的任务集合 |

### 核心公式

```
Eval = Agent Input → Execution → Capture (Trace + Output) → Check Rules → Score
```

## 三类 Grader

| 类型 | 机制 | 成本 | 稳定性 | 适用场景 |
|------|------|------|--------|---------|
| 确定性 Grader | 脚本、断言、Lint、AST | 毫秒，免费 | 100% | 文件存在、编译通过、测试通过 |
| LLM-as-Judge | LLM + 结构化 prompt + JSON Schema | 秒，API 成本 | 有抖动 | 代码风格、意图匹配、解释清晰度 |
| 人工 Grader | 领域专家 + 标注指南 | 分钟到小时 | 取决于标注者 | 校准 LLM 判断、异常诊断 |

**优先级：确定性 > LLM > 人工。能用代码判断的绝不用模型，必须用模型时用人工校准。**

### 人工 Grader 的 6 个适用场景

1. 校准 LLM 判断（最重要，100-200 样本，要求 ≥85% 一致性）
2. 主观任务评分
3. 诊断异常通过率（0% 或 100% 通常意味着任务/Grader 有问题，不是模型不行）
4. 新评测集的 Ground Truth 标注（前 20-50 个参考解）
5. 每周 Trace 抽样审计
6. 高风险领域（医疗/金融/安全，100% 人工审核）

## 两个关键概率指标

### pass@k

- 定义：k 次尝试中至少成功一次的概率
- 含义：能力上限
- 特点：k 越大分数越高
- 适用：编码场景（首次成功）

### pass^k

- 定义：k 次尝试全部成功的概率
- 含义：稳定性/一致性
- 特点：k 越大分数越低
- 适用：面向用户的 Agent（一致性很重要）

**示例：** 如果单次成功率 75%，pass^3 = (0.75)^3 ≈ 42%。k=10 时 pass@k 趋近 100%，pass^k 趋近 0%。

## 五维度评测体系（腾讯）

| 维度 | 优先级 | 评测方式 | 权重 |
|------|--------|---------|------|
| 功能正确性 | P0 | 确定性 | 30% |
| 过程质量 | P1 | LLM-as-Judge | 25% |
| 效率成本 | P1 | 确定性 | 15% |
| 鲁棒安全 | P0 | 确定性+LLM | 20% |
| 体验对齐 | P2 | LLM-as-Judge | 10% |

### 功能正确性（P0）

- pass@1 / pass^k
- 任务完成率
- 指令遵循（JSON Schema 验证、正则匹配）
- 工具调用正确性

### 过程质量（P1）

- 推理合理性（1-5 分）
- 步骤最优性（实际 vs 参考步骤数比）
- 信息完整性（关键点覆盖率）
- 上下文利用度
- 自修正能力

### 效率成本（P1）

- Token 消耗（avg/p95）
- 工具调用次数（avg/p95）
- 端到端延迟（p50/p95/p99）
- 失败重试率
- 每任务成本（元）

### 鲁棒安全（P0）

- 一致性/稳定性（pass^k，k=5/10）
- 故障恢复（故障注入测试）
- 注入抵抗（红队 prompt 注入测试）
- 幻觉率
- 权限升级风险
- PII/合规违规
- 拒绝合理性

### 体验对齐（P2）

- 语气/风格
- 清晰度
- 主动澄清
- 同理心
- 可解释性
- 用户满意度（CSAT/NPS）

## 100 分扣分制（腾讯）

- 起始 100 分
- 通过阈值：80 分（可调）
- 任务结果不匹配：-100 分（直接失败）
- 每步偏差：-10 分
- 时间超基线（5 分钟）：每多 1 分钟 -10 分
- 稳定性：跑 N 次（推荐 N=5），全部通过取平均；任意一次失败则 0 分

## 测试用例设计（四层递进）

1. **Trigger**：Skill 是否正确激活？负面用例测试相似但无关的 prompt 不应触发
2. **Core Logic**：执行过程是否正确？最大类别（2-3x 其他），三步法：画所有分支路径 → 每分支至少 1 用例 → 加组合和边界用例
3. **Output Quality**：最终产出是否完整、准确、可用？检查文件存在、内容准确、格式合规、无幻觉
4. **Error Tolerance**：Agent 能否优雅处理异常输入、边界条件、环境故障？

## 能力评测 vs 回归评测

| 类型 | 目标 | 通过率 | 何时运行 |
|------|------|--------|---------|
| 能力评测 | "Agent 能做什么？" | 从 20-50% 起步，逐步提升 | 开发时 |
| 回归评测 | "Agent 还能做以前能做的吗？" | 目标 ~100% | 每次 CI |

当能力评测稳定在 100% 时，"毕业"到回归套件。Anthropic 建议：确定性任务 100%，非确定性任务 ≥95%。

## 基线建立

1. 跑一次 Agent，人工确认结果可接受
2. 那次运行成为基线快照
3. 基线包含：预期过程（推理链、工具调用序列、中间产物、完整 Trace）+ 预期结果（最终输出、输出文件、输出报告）
4. 基线同时服务确定性 Grader（程序化对比）和 Rubric Grader（作为 LLM 参考答案）

## 评测驱动开发

> 先建评测定义期望能力，再迭代直到表现达标。

Anthropic 的做法：产品经理、客户成功、甚至销售都通过 Claude Code 提交评测任务的 PR。评测是研究和产品团队之间的桥梁。

## 关键洞察

1. **评测结果不匹配 → 先查 Grader bug**：Opus 4.5 在 CORE-Bench 上从 42% 跳到 95%，只是因为修了 Grader 的 bug
2. **读 Transcript 是关键**：不读大量试运行记录和分数，就无法知道 Grader 是否正确
3. **监控饱和度**：100% 通过率的评测只能追踪退化，不能提供改进信号
4. **平衡测试集**：必须同时测试"应该做"和"不应该做"的用例
5. **环境隔离**：每次试运行从干净状态开始，残余文件/缓存引入噪声
6. **20-50 个任务就够开始**：早期变化效果大，小样本足够
